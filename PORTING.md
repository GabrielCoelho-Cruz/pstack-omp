# pstack on omp, the port

## Upstream truth and the pinned baseline

The true upstream is **`cursor/plugins`, subdirectory `pstack`** (MIT). This repository is the
source of truth for the omp port. The old generator flow that built the port from a local `pstack`
tree is retired, so the files here are the artifact.

The baseline is one file, `omp-port/UPSTREAM`, holding the full 40-hex sha of the upstream commit
the port is synced to. Nothing else records it. Every derived field is generated by
`omp-port/sync-upstream.sh` from that sha, from the live tree, and from the port version counter
described under [Versions and releases](#versions-and-releases): the plugin version in
`plugins/pstack/package.json`, the versions in `.omp-plugin/marketplace.json`, and the `pstack`
catalog description with its skill, playbook, principle, and agent counts.

**Third-party mirrors of `pstack` are not upstream.** Build and diff only against
`cursor/plugins`. A mirror lags canonical, and every parity claim made against one inherits that
lag.

### What the build takes from upstream, and what it leaves

The build extracts exactly `pstack/skills` and `pstack/agents` from the pinned commit. Everything
else upstream ships is omitted on purpose:

- **Manifests.** `.cursor-plugin/plugin.json` and its logo are Cursor marketplace metadata with no
  omp consumer. They are not carried and not rewritten. The omp plugin identity is
  `plugins/pstack/package.json` plus the catalog.
- **The guide.** Upstream's `docs/guide/` pages are not shipped, and no shipped file may depend on
  one. `poteto-help` routes to shipped skills, the plugin README, and omp's own documentation. A
  historical upstream link is tolerated only when it uses the full pinned sha and is labelled as
  upstream's own Cursor-specific page.
- **Automations.** `automations/benny` is Cursor Automations and Bugbot wiring and is inert here.

Treat the port as prose mirrored and mechanics substituted, not as the Cursor plugin installed.

### Drift check

```bash
bash omp-port/sync-upstream.sh check
```

Empty output and exit 0 mean no drift since the pin. Each line is an upstream commit that touched
`pstack/`, newest first, as short sha then date then subject. The resolved target is the newest
commit that touched `pstack/`, printed to stderr, and written to the file named by
`SYNC_TARGET_OUT` when that variable is set. The workflow reads it from there instead of resolving
the head a second time and getting a different answer.

## The build

The port is a build, not a maintained tree. `plugins/pstack/skills` and `plugins/pstack/agents` are
upstream text at the pinned sha, in this order:

1. `omp-port/rules.sed`, the ordered substitution table, one `sed -E` rule per line.
2. `omp-port/patches/*.patch`, applied in lexical order with zero fuzz. A change no substitution can
   express belongs here.
3. Catalog visibility, which drops upstream's hide flag from every workflow skill and keeps the
   reference-only skills hidden.
4. Preparation, `prepare_tree` in `omp-port/lib.sh`. It restores every path in `omp-port/owned.txt`
   from the current worktree, so an uncommitted owned edit survives the build, and falls back to
   the exact path at `HEAD` only when the worktree lacks it. A path missing from both is an error.
   It then copies `agents-extra/*.md` into `agents/`, requiring exactly the six routing names and
   rejecting any collision with an upstream agent.

`build_tree(sha, work)` and `prepare_tree(work)` only ever write the scratch directory they are
given. The gate and the sync script call the same two functions, so the tree the gate compares is
the tree the sync would install.

A hand edit under `skills/` or `agents/` fails the gate's `reproducible` check, which rebuilds the
pin and diffs each directory against the tree, and the next build deletes it. Put the change in
`rules.sed`, in a patch, or in an owned path instead.

The owned roots are `skills/omp-mechanics`, `skills/pstack-omp`, `agents-extra`, `extensions`,
`README.md`, `LICENSE`, and `THIRD_PARTY_NOTICES.md`, all under `plugins/pstack`. `agents/` is
generated and never owned. `omp-mechanics` and `pstack-omp` carry the port's prose and the runtime
adapter, so the omp-specific levers sit in two skills the injected reminder points every agent at,
instead of being sprinkled through files upstream keeps rewriting.

### Versions and releases

The port version is its own stable counter, `plugins/pstack/package.json` `.version`, a plain
`MAJOR.MINOR.PATCH` with no leading zero in any component and no build metadata. It is written to
that file, to the catalog `metadata.version`, and to both plugin entries. `fan-out` is hand-written,
has no package manifest, and takes its version from the same counter. Upstream's own version is
printed in the sync output as provenance and feeds nothing.

| Command | Pin | Version |
|---|---|---|
| `bash omp-port/sync-upstream.sh rebuild` | unchanged | unchanged |
| `bash omp-port/sync-upstream.sh release` | unchanged | patch + 1, once |
| `bash omp-port/sync-upstream.sh [<target-sha>]` | moves to the target | patch + 1, once |
| the same, with a target equal to the pin | unchanged | unchanged, nothing is touched |
| `bash omp-port/sync-upstream.sh recover` | unchanged | unchanged, settles an interrupted install |

`release` is the port-only release, for a change to `rules.sed`, `patches/`, `owned.txt`, or an owned
path. Every release increments the patch component by one even when upstream keeps or lowers its
own version, so a published version is never reused or lowered. The scripts refuse to advance when
the package and the catalog disagree. A catalog entry that has no version yet is initialised by the
next install.

### Installing safely

An install is a transaction on the destination filesystem. `sync-upstream.sh` builds the tree into a
scratch directory beside the git directory, runs `prepare_tree`, copies the current package manifest
into it, and prepares the package, catalog, and pin bytes. Only after the JSON validates and every
owned source is present does it touch the live files:

1. Back up the live catalog and pin, and mark the backups complete.
2. Move the live plugin directory aside, move the prepared one in, then replace the catalog and the
   pin with single renames.
3. Mark the transaction committed, stage the result in git, and delete the backups.

A failed build, a missing owned source, a failed metadata write, or a failed rename leaves the old
plugin, catalog, pin, and index as they were, and the script cleans its scratch state. It traps
`EXIT`, `INT`, `TERM`, and `HUP` and rolls back from them. Three renames are not one atomic
operation, so a kill the script cannot trap leaves its backups and a marker in the git directory.
The next invocation of any installing mode restores the previous complete installation before it
looks at the tree, and a transaction that had already committed is finished and staged instead.
`bash omp-port/sync-upstream.sh recover` does the same on demand. Nothing is staged in git before the
filesystem transaction commits.

Everything under `plugins/pstack` is either generated, owned, or the manifest, because the whole
directory is replaced. A stray file anywhere else stops the install instead of being deleted.

### How to re-sync

The `upstream-sync` workflow runs daily and on demand. In order, it:

1. Validates an explicit `sha` input before it decides the run is empty, so a valid explicit target
   runs even when the default drift query finds nothing. A different open sync PR blocks a competing
   target. The PR for the same target never blocks its own recovery.
2. Tells a missing sync branch from an unreachable remote. `git ls-remote` exit 2 is a missing
   branch, any other failure stops the run.
3. Runs `check-port.sh` and the extension tests on `main`, so a red trunk stops the run.
4. For a new target, runs the sync and commits it. A sync that fails produces no artifact, and
   nothing is pushed. For a branch a prior run pushed, it checks out that exact branch, requires its
   pin to match the target, and carries on, so a missing PR is created and an open one is reused.
5. Fetches `origin/main`, rebases the sync branch onto that exact tip with no automatic conflict
   resolution, and runs the full gate and the extension tests against the rebased tree. It pushes with
   a head-safe lease when the history changed, records the tested base sha and tested head sha, and
   opens or updates the PR with the sync and gate output.
6. Fetches `main` again immediately before merging. If it advanced, the rebase and the gate repeat,
   or the run fails without merging. Otherwise it merges only the tested head, with
   `gh pr merge --match-head-commit <tested-head> --squash --delete-branch`.

A conflict, a red gate, or a failing test leaves the PR open for a human with the output in its body.
Squash merging is safe because `omp-port/UPSTREAM`, not the branch history, carries the base for
the next build.

The workflow does not rely on any event that a token-created push or PR would have triggered, since
those do not fire workflows. It runs the gate and tests itself, after the rebase. `gate.yml` stays
the normal independent gate on every pull request and every push to `main`, and runs the extension
tests too.

One race remains on the host side. The recheck of `main` just before the merge narrows the window
but is not a compare-and-swap of the base branch. Closing it needs branch protection with required
up-to-date checks, or a merge queue, on the host. The local recheck does not supply that.

A maintainer runs `bash omp-port/sync-upstream.sh [<target-sha>]` for the same build locally, target
defaulting to the newest commit that touched `pstack/`, or `release` or `rebuild` as above. A target
that never touched `pstack/` is refused, because the next run has to find that sha again in the
path-filtered history. Then run `bash omp-port/check-port.sh` and commit.

The scripts assume GNU `sed` and coreutils, as on the CI runner. On macOS, install them with
`brew install gnu-sed coreutils` and put
`/opt/homebrew/opt/coreutils/libexec/gnubin:/opt/homebrew/opt/gnu-sed/libexec/gnubin` first on
`PATH`. BSD `sed` rejects `rules.sed` and BSD `chmod` has no `--reference`.

### Rebasing a patch

A rule edit or an upstream change can stop a patch from applying. Never fix it by editing generated
files. Rebase it in a throwaway Git repository:

1. Save the old rules and old patches first. Build the pin's rules-only text, commit it as the old
   base, then apply each old patch in lexical order, one commit each. A patch's old postimage is its
   intent.
2. Build the same pin with the new rules, or the new upstream pin when syncing, into a second
   scratch tree and commit it as the new base.
3. Cherry-pick the old patch commits onto the new base with three-way conflict context. Keep
   upstream's wording and implement the current runtime contract. A deleted intermediate patch is
   omitted, and the later one is reconciled against its pre-intermediate base.
4. Re-diff each resolved commit against its immediate parent into the matching
   `omp-port/patches/*.patch`, then apply all of them afresh with `patch -p1 --fuzz=0`. No `.rej`,
   backup, or conflict marker may ship. Remove a patch only when its whole effect is obsolete.

## The gate

`bash omp-port/check-port.sh` fails closed. Every `grep`, `diff`, and `cmp` it relies on is read
for its status: 0 is a match or equal, 1 is no match or changed, anything higher is an inspection
failure that fails the check and the run. A reproduction that cannot reach the canonical checkout or
cannot build is a failure everywhere, never a skip, so a PASS always includes `reproducible`.

It scans both plugins, the extension sources, the root `README.md`, and this file. It also checks
the contracts the package makes:

- every shipped Markdown link resolves, `skill://` references included, and none escapes its plugin;
- `task.agentModelOverrides` is named in both `setup-pstack` and `poteto-mode`, each checked alone;
- the seven routed skills point at `skill://pstack-omp` and the setup reference;
- the six routing agents in `agents-extra/` and `agents/` are exactly the settled set, identical,
  and carry no model, thinking, blocking, spawns, or tools field;
- the notices match the root notices, the reference-only skills are hidden, and the reply and
  correction skills stay visible;
- the package, catalog, and both plugin entries agree on one version, and the counts, pin, and
  agent count in the catalog match the tree;
- no task `environment` field, legacy multi-select field, tool-shaped peer-messaging call,
  prescribed per-call model, retired install root, merge conflict marker, or pointer to the omitted
  guide survives.

`omp-port/slug-allowlist.txt` lists the few lines a pattern may skip, each tied to one pattern on
one line, and the gate fails an entry whose line no longer trips its pattern.

## Install, the two live shapes

Both shapes load the same plugin. Neither needs an agent symlink into a native root.

**Link, the maintainer shape.** `omp plugin link <checkout>/plugins/pstack` registers the checkout,
so skills and agents load straight from the working tree and a re-sync is live after
`/reload-plugins`.

**Marketplace, the user shape.**

```
/marketplace add <checkout-or-marketplace-url>
/marketplace install pstack@pstack-omp
/reload-plugins
```

The install caches the plugin and registers it, with its `skills/`, its `agents/` subtree, and the
`potetomode` extension named by `package.json` `omp.extensions`. Omp-origin marketplace roots are
exempt from the opt-in that foreign-user agent sources need, so the routing agents,
`poteto-agent`, and `comment-sicko` are discovered with no extra step. `/reload-plugins` picks up
skills and agents after an interactive install, and a restart loads the new extension module. Do not
enable unrelated foreign plugin sources to make discovery work.

Check discovery in a fresh session with the probe in `plugins/pstack/README.md` instead of trusting
a recorded result. A discovery result belongs to the runtime that produced it.

### Installed agents

Eight agents ship. Six are the routing agents, model-free definitions whose names are the exact
keys of the setting below. `poteto-agent` and `comment-sicko` are the compatibility agents upstream
ships, carried through `agents/`. Each routing agent has one source in `plugins/pstack/agents-extra/`,
copied to `agents/` by `prepare_tree`.

### Visibility

Upstream marks almost every skill `disable-model-invocation: true`, which omp maps to `hide`. The
build keeps the model's skill list useful: it drops the flag from every workflow skill and keeps it
on the 24 `principle-*` leaves and `make-bot-ui`, while `omp-mechanics` carries its own. A hidden
skill is still loaded and reachable through `skill://<name>`, and through `/skill:<name>` when skill
commands are enabled. Listing, explicit invocation, and persistent pinning are three different
things. `bro`, `ketchup`, `in-your-own-words`, and `correct` stay listed.

`make-bot-ui` is unsupported on omp for routine creation, secrets, and webhook waking, and its
source steps are not runnable instructions. See
`skill://omp-mechanics/references/make-bot-ui-on-omp.md`.

## Where the port's changes live

`omp-port/rules.sed` is the substitution table, with tiered rules for the model slugs upstream names
first and a catch-all under them. The sync and the gate report each slug only the catch-all rewrote
as `untiered`, so it can earn a tiered rule. `omp-port/patches/` carries the port's own code as
unified diffs applied after the rules. The files in `omp-port/owned.txt` are the port's own prose and
code.

## Substituted mechanics

### One model-routing mechanism

Model choice is `task.agentModelOverrides[exactAgentName] = concreteSelector`, one settings record.
The six routing agents are the only keys setup owns:

| Agent | Used for |
|---|---|
| `pstack_fast` | fast code and mechanical work, explorers, investigators, swarm workers, delegated implementers |
| `pstack_judgment` | judgment and prose, explainers, synthesizers, reviews, the hardest delegated tasks |
| `pstack_panel_1` to `pstack_panel_4` | diverse-model panel slots for arena, architect, interrogate, reflect divergent, and swarm race arms |

Routed skills select the matching shipped agent through the task `agent` field and send no worker
model of their own. Setup, `skill://setup-pstack`, writes the record from `omp models --json`,
replaces or removes only those six keys, preserves every other override and record, and never
persists an inherit or auto placeholder as a model. Omitting a key means the agent inherits the
parent. Precedence is the settings override, then agent frontmatter, then the parent or configured
fallback, and extension routing or retry fallback can still change the final model, so a result's
reported model is the evidence, not the configuration.

Panel slots are reusable. Arena, architect, and interrogate use the configured slots in numeric
order and add the lowest missing ones until two exist, so an unconfigured install still runs two
independent contexts without promising two different models. An explicit larger count repeats the
selected slots round-robin under unique task names. `skill://pstack-omp` separates this from the
generic canonical-role fallback and refuses to claim a route took effect when discovery or policy
blocked the exact agent name. The authoritative format is
`skill://omp-mechanics/references/setup-pstack-config.md`.

The vibe adapter exposes only `fast` and `good`, so per-role task routing is not available there.
The unrelated `sonic` and `task` overrides are left alone.

`poteto-agent` ships model-free and inherits the chat model. To pin it, add `model: "@poteto"` to its
frontmatter and bind that alias through `modelRoles`, or set
`task.agentModelOverrides[poteto-agent]`. Precedence is the override, then the frontmatter alias,
then the parent. A literal inherit placeholder is not a usable model value. Bind a real selector
that `omp models` reports for the machine in front of you.

One observation worth keeping, as a historical measurement and not a rule. On one local deployment,
a thinking model under a small token budget could spend all of it in its reasoning field and return
empty content, which made wide fan-outs unreliable: 9 of 12 with thinking against 24 of 24 and 40 of
40 with the thinking template off for the same prompt shape. It says nothing about any other model or
setup.

### Peer coordination and process supervision

No skill uses the old tool-shaped peer-messaging and process-supervision tool. The replacements, from the omp tool documentation:

- `read history://` lists registered agents and transcripts. `read proc://` lists visible jobs,
  running agents that have no job row, and project services. Messages self-deliver, and there is no
  inbox-drain tool.
- Send a message with `write` to `agent://<returned-id>`, or `agent://all` for an intentional
  broadcast. Read agent output at `agent://Parent.Child`, and structured output at
  `agent://Parent.Child/reports/0/data`.
- A long-running process is a named `bash` service with a project-unique `name`, `command`, optional
  `cwd`, and `ready`. Do not combine a name with `async` or a timeout. Read it at
  `proc://<service-name>`, send stdin with `write` to `proc://<service-name>`, stop a job with
  `write` to `proc://<id>/kill` and no content, and set its lifetime with `write` to
  `proc://<name>/mode` using `persist`, `session`, or `detached`.
- A finite check is an ordinary `bash` call. `async: true` defers it where the schema exposes it,
  the command deadline still applies, and `timeout: 0` is for an intentionally unbounded job.
- The `wait` tool takes no arguments and returns on the first owned result, message, or interrupt.
  Use it only when blocked and account for each required result separately. Eval's
  `wait(handles)` is a different function that returns results in input order.

### Local isolation

Cloud agents become local `isolated: true` subagents when `task.isolation.enabled` is on and plan
mode is off. The parent must run inside a git checkout, and a spawn outside one fails fast instead
of sharing the checkout. A kept-alive isolated agent keeps its workspace through idle and parked
states and revives in-process on a direct message. Release captures the final changes and cleans the
workspace. A hard abort is terminal. After a host restart isolated children cannot be cold-revived,
so reconcile the durable artifacts and dispatch replacement work. The task tool rejects an
`environment` field, any cloud base-branch field, and a per-spawn model.

### Scheduling and waking

There is no shipped routine or webhook service. External work can still reach a session through
authenticated RPC `prompt`, `steer`, or `follow_up`, or through an extension. A named service
observes work only while its session exists and is not a scheduler. For unattended work, use launchd
on macOS, or a systemd user timer or cron on Linux, connected to an explicit CLI or RPC entry point,
and do not substitute one OS's scheduler for another. Inspect the live loop help before prescribing
loop grammar or cadence. No skill promises an hourly timer.

### The pin extension

The poteto-mode pin is a port extension, `plugins/pstack/extensions/potetomode/index.js`, declared
by `package.json` `omp.extensions`. It persists the pin with `appendEntry`, rebuilds it from the
active branch on `session_start`, `session_branch`, and `session_tree` without appending an entry,
injects the reminder in `before_agent_start`, and registers `/poteto-mode on|off|status` and
`Alt+Shift+T`. Reset of activity happens on session start only. The `--poteto` flag decides when the
branch holds no entry. The reminder is a pointer, not the playbook: it tells the agent to read
`skill://poteto-mode`, `skill://omp-mechanics`, and `skill://pstack-omp` on demand.

Whether a given omp build also interprets upstream's `mode:` and `reminder:` frontmatter is a
runtime property, so do not read it off a version number. Probe the binary:

```
grep -c -a -F 'Pin or unpin a mode skill' "$(command -v omp)"
```

Zero means the extension is what pins the mode. Nonzero means native handling exists, both injectors
would fire and collide, and the extension should be removed or gated. The same rule applies to every
capability here: state the probe, not a version.

## Known deltas the port mirrors faithfully

The upstream guide says the verification feature map lives at `references/features` while both
trees write `features/`, and it recommends a daily `/maintain-verification-skill` run while both
trees state no cadence. The port does not diverge on either.

## Honest limitations

- **Graphite.** The stacking commands in Shipping, Babysit, Autopilot-stack, and Orchestrate name
  `gt`. Where that CLI is absent they cannot run as written, and single-PR flows through `gh` still
  work. Upstream now lands through GitHub by default, which reduces the exposure.
- **Isolation is opt-in per spawn.** Absent `isolated: true` a worker shares the parent checkout, so
  each swarm brief that needs separation must request it, and the setting above must be on.
- **Unrun dispatch.** A green static gate says nothing about a model dispatch or a webhook service
  that was not run. Routing is proved by a real dispatch that reports each resolved model and
  whether a fallback applied.
- **Measurements are historical.** The numbers retained in the skills are observations on one setup
  at one time, not reliability floors and not causal claims.
